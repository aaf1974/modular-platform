# Архитектурные решения платформы

> Статус: согласованные направления для текущего этапа разработки. Документ фиксирует архитектурные решения и ограничения; он не утверждает, что все описанные будущие изменения уже реализованы в коде.

## 1. Модули и их границы

### Решение

- Хост приложения — composition root: он явно выбирает и регистрирует системные и бизнес-модули, WebFeature, конфигурацию и инфраструктурные интеграции.
- `IModule` остаётся базовым контрактом модуля. Зависимости модулей объявляются явно через `IModuleDependencies`; платформа проверяет наличие обязательных типов модулей, но не регистрирует их автоматически.
- `ValidateModules()` следует вызывать после регистрации всех модулей и до `Build()`.
- Различие между системными и бизнес-модулями пока является архитектурной классификацией, а не отдельными runtime-контрактами. Не вводить `ISystemModule` и `IBusinessModule`, пока от них не зависит проверяемое поведение.
- Contracts-сборку создавать только при наличии реального публичного контракта, на который должны ссылаться другие модули без зависимости от реализации.
- Бизнес-модуль может включать несколько сборок и интегрироваться с внешними системами через Saga или другой подходящий механизм координации. Количество сборок само по себе не определяет границу модуля.

### Следствия

- Регистрация модулей остаётся явной; автоматическое сканирование сборок не вводится.
- Платформа проверяет зависимости модулей, но не пытается анализировать все зависимости DI-сервисов.
- Отсутствующие зависимости должны приводить к понятной ошибке при валидации до запуска приложения.

## 2. Общий `ApplicationDbContext`

### Решение

Сохранить единый `ApplicationDbContext` для сущностей подключённых модулей в рамках одного приложения.

### Следствия

- Итоговая EF-модель формируется из модулей, подключённых конкретным хостом.
- Модули отвечают за конфигурации собственных сущностей и не должны без необходимости перенастраивать сущности других модулей.
- Миграции создаются и проверяются для итоговой модели приложения, а не рассматриваются как полностью независимые миграции каждого модуля.
- Состав модулей, влияющих на EF-модель, должен быть известен при построении модели. Ключ кэша модели обязан учитывать различия наборов модулей и сборок конфигураций.
- Фильтр soft delete применяется к корневым сущностям, реализующим `ISoftDeletable`; owned-типы полагаются на фильтрацию владельца. Пользовательские query filters должны сохраняться и объединяться с фильтром soft delete.
- Удаление сущности, реализующей `ISoftDeletable`, выполняется логически. Для сущностей без этого контракта сохраняется обычное физическое удаление.

Отдельные контексты следует пересматривать только при появлении конкретной потребности в независимом владении схемами, изоляции транзакций или отдельном жизненном цикле хранения.

## 3. Жизненный цикл сборки приложения

### Решение на текущем этапе

Оставить стандартный ASP.NET Core builder и явную последовательность регистрации. Вызывать `builder.Services.ValidateModules()` непосредственно перед `builder.Build()` после регистрации всех модулей.

Extension-метод не может перехватить вызов instance-метода `WebApplicationBuilder.Build()`, поэтому одной extension-обёрткой нельзя гарантировать выполнение проверки.

### Возможное развитие

Прототипировать небольшой `PlatformApplicationBuilder` с методом `BuildPlatform()` только после тестового сравнения с текущим подходом. Цель — централизовать обязательную валидацию и платформенный жизненный цикл, а не просто переименовать стандартные API.

Перед принятием такого API проверить:

- ошибки зависимостей останавливают сборку до создания приложения;
- сохраняется доступ к `IServiceCollection`, конфигурации, окружению и стандартному хосту;
- не усложняется использование `WebApplicationFactory` и сторонних библиотек;
- ясно, обязателен ли `BuildPlatform()` или является только удобным методом.

До завершения этого эксперимента собственный builder не считается частью публичного API платформы.

## 4. `WebFeature` и `IWebModule`

### Разделение ответственности

- `IPlatformWebFeature` предназначен для общей, повторно используемой веб-функциональности. Он может регистрировать сервисы до `Build()` и конфигурировать приложение после `Build()`.
- `IWebModule` используется модулем, которому необходимо настраивать HTTP-конвейер. Сам по себе `IWebModule` необязателен для бизнес-модуля.
- Порядок регистрации DI-сервисов и порядок middleware — разные вопросы и должны документироваться и тестироваться отдельно.

### Обработка исключений

`DefaultExceptionHandler` остаётся частью базовой веб-инфраструктуры, а не обычной необязательной `WebFeature`. Единая обработка необработанных исключений должна подключаться платформой в известной ранней позиции и не должна случайно исчезать из-за отсутствия feature.

Если понадобится замена обработчика, следует предусмотреть одну явную точку настройки или замены. Не вводить параллельно два независимых механизма включения exception handler.

### Порядок middleware

Текущее поведение сохраняется до отдельного изменения API:

1. `UseModules()` подключает exception handler.
2. Затем настраиваются `IPlatformWebFeature` в порядке регистрации.
3. Затем настраиваются модули, реализующие `IWebModule`, в порядке регистрации.
4. Положение самого `UseModules()` относительно других вызовов `Use...` остаётся ответственностью хоста.

Поскольку порядок влияет на безопасность и поведение запросов, следующим изменением следует спроектировать явный `Order` для `IPlatformWebFeature` и `IWebModule` одновременно. Предпочтительная начальная модель — сортировка по `Order` со стабильным порядком регистрации при равных значениях. Перед реализацией нужно закрепить контракт тестами.

Не вводить сложный граф зависимостей middleware заранее. Если числового `Order` окажется недостаточно для обязательных отношений (например, authentication до authorization), добавить явные ограничения и проверку конфликтов отдельным решением. Базовый exception handler должен иметь зарезервированную позицию и не конкурировать с пользовательскими приоритетами.

## 5. Диагностика и документация API

### Решение для хоста

- Разделять liveness и readiness.
- Liveness отвечает на вопрос, работает ли процесс, и не должен становиться неуспешным только из-за временной недоступности базы данных.
- Readiness проверяет зависимости, критичные именно для данного приложения. Состав таких проверок определяет хост, а не универсальная конфигурация платформы.
- Не публиковать подробные диагностические данные, секреты и внутренние исключения неавторизованным клиентам. Доступ к Health Checks UI и подробным endpoint должен быть ограничен политикой хоста и окружением.
- Swagger/OpenAPI по умолчанию включать только в Development, если хост явно не выбрал другую политику.

Эти правила являются рекомендациями и целевым контрактом конфигурации хоста; они не означают, что текущая реализация автоматически создаёт все перечисленные endpoints или защищает их.

## 6. Проверки и критерии принятия изменений

Архитектурные изменения сопровождаются тестами на наблюдаемое поведение, а не только на внутреннюю реализацию.

Минимальные критерии:

- обязательные зависимости модулей валидируются до `Build()`;
- порядок конфигурации WebFeature и веб-модулей закреплён тестами;
- при введении `Order` проверяются сортировка, стабильный порядок при равных значениях и ошибки некорректной конфигурации;
- кэш модели EF Core проверяется для разных наборов модулей при одинаковых `DbContextOptions`;
- soft delete и аудит проверяются как на уровне `ChangeTracker`, так и через сохранение и повторную загрузку из PostgreSQL;
- диагностические endpoints проверяются на ожидаемую семантику и правила доступа;
- документация различает реализованное поведение, принятые решения и будущие предложения.

## 7. Что пока не вводится

- Отдельные runtime-интерфейсы `ISystemModule` и `IBusinessModule`.
- Обязательная Contracts-сборка для каждого модуля.
- Отдельный `DbContext` на каждый модуль.
- Автоматическое сканирование сборок для регистрации модулей.
- Собственный builder и `BuildPlatform()` до проверки прототипа.
- Сложный граф зависимостей middleware без подтверждённой необходимости.
- Автоматическое включение универсального набора readiness-проверок для всех хостов.

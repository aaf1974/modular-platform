# Предложения по развитию архитектуры

> Этот документ фиксирует направление обсуждения, а не существующий публичный API. Реализация предложений должна начинаться с тестов и отдельного решения по контрактам.

## 1. Системные и бизнес-модули

Различие между системным и бизнес-модулем — прежде всего смысловое, а не требование к количеству сборок или обязательным маркерным интерфейсам.

- **Системные модули** реализуют повторно используемые возможности хоста: например, аутентификацию, авторизацию или интеграционные механизмы. Они могут публиковать отдельную Contracts-сборку, если другие модули действительно должны ссылаться на публичные интерфейсы и DTO.
- **Бизнес-модули** реализуют предметные сценарии конкретной системы. Один модуль может состоять из нескольких сборок или использовать Saga/другой механизм координации для интеграции с внешней системой.
- **Хост приложения** собирает нужные системные и бизнес-модули. Не следует автоматически вводить `ISystemModule` и `IBusinessModule`: маркеры оправданы, только если на них опирается проверяемое поведение платформы.
- Contracts-сборку не нужно создавать механически для каждого модуля. Она полезна при наличии стабильного публичного контракта, который должен быть доступен без ссылки на реализацию.

## 2. Один ApplicationDbContext

Общий `ApplicationDbContext` для сущностей подключённых модулей — осознанный выбор платформы, а не временная ошибка архитектуры. Он упрощает единицу работы и транзакции между сущностями разных модулей, но усиливает связь модулей на уровне общей модели и миграций.

Практические следствия:

- набор модулей, влияющих на EF-модель, должен быть известен при построении модели и стабилен в рамках хоста;
- миграции формируются для итоговой модели приложения, а не независимо каждым модулем в вакууме;
- модули должны владеть конфигурациями своих сущностей и избегать случайной конфигурации чужих типов;
- интеграционные тесты должны проверять итоговую модель и миграции хоста.

Переход к отдельным контекстам следует рассматривать только при появлении конкретных требований к независимому владению схемами, изоляции транзакций или независимому жизненному циклу хранения.

## 3. Собственный builder и BuildPlatform

### Предлагаемое направление

Рассмотреть небольшой собственный объект конфигурации/сборки приложения (например, `PlatformApplicationBuilder`), который инкапсулирует стандартный `WebApplicationBuilder`, предоставляет платформенные операции регистрации модулей и завершает конфигурацию через `BuildPlatform()`.

Одна из целей — гарантировать вызов `ValidateModules()` после регистрации всех модулей, но до фактического построения приложения. Валидация внутри `AddModule()` не подходит: зависимости могут быть зарегистрированы позже. `IHostedService` тоже поздно — приложение уже построено, а часть инфраструктуры может начать запускаться.

### Плюсы

- единая, заметная точка сборки платформенного приложения;
- меньше риска забыть обязательные проверки и стандартные шаги старта;
- можно централизовать правила порядка регистрации и диагностические сообщения;
- хост получает более короткий `Program.cs` и меньше деталей платформенной сборки.

### Минусы и критика

- появляется собственная абстракция поверх стандартного ASP.NET Core builder API: разработчикам нужно изучить её и понимать, когда использовать `Builder.Services`, `Configuration`, `Environment` и стандартный `Build`;
- риск обёртки ради одной проверки: если класс только переименовывает стандартные методы, он добавляет сложность без существенной пользы;
- интеграция с `WebApplicationFactory`, сторонними библиотеками и примерами ASP.NET Core должна оставаться простой;
- важно не скрывать доступ к обычному `IServiceCollection` и стандартному хосту;
- нужно решить, будет ли `BuildPlatform()` единственным поддерживаемым путём или просто удобным методом. Нельзя обещать обязательную валидацию, если приложение всё ещё может незаметно обойти её вызовом стандартного `Build()`.

### Рекомендуемый эксперимент

До реализации API описать минимальный жизненный цикл и написать тесты: ошибки отсутствующих зависимостей останавливают сборку до создания `WebApplication`; корректный набор модулей строится; стандартные конфигурация, окружение, logging и тестовый хост не теряются. Затем сравнить обёртку с альтернативой — обычный `builder.Services.ValidateModules()` непосредственно перед `builder.Build()`.

Не перехватывать и не переопределять `WebApplicationBuilder.Build()` extension-методом: методы расширения не могут перехватить вызов существующего instance-метода.

## 4. WebFeature и обработка исключений

`WebFeature` предназначен для подключения общей, повторно используемой веб-функциональности, которая обычно настраивает сервисы до `Build()` и приложение после `Build()`.

`DefaultExceptionHandler` по умолчанию разумно оставить частью базовой веб-инфраструктуры, а не обычной необязательной feature: единая обработка необработанных исключений — платформенный инвариант и должна стоять достаточно рано в middleware pipeline. Если она станет просто одной из feature, её можно случайно исключить или поставить после middleware, которое уже выбрасывает исключение.

Если в будущем потребуется заменить обработчик, предпочтительнее предусмотреть явную точку настройки/замены handler в `PlatformOptions` или встроенную обязательную feature с зарезервированным приоритетом. Не следует одновременно иметь два конкурирующих механизма включения обработки исключений.

## 5. Явное упорядочивание WebFeature и IWebModule

Порядок middleware — значимая часть поведения приложения. Сейчас порядок вызовов в `UseModules()` определяется порядком регистрации feature, затем веб-модулей; кроме того, `UseModules()` сам устанавливает exception handler до этих вызовов.

Предлагается в будущем добавить явный порядок к обоим контрактам, но не вводить сложный dependency graph без реальной необходимости:

- `IPlatformWebFeature`: целочисленный `Order` либо отдельные метаданные регистрации;
- `IWebModule`: аналогичный `Order` для конфигурации HTTP-конвейера;
- сортировка по `Order`, затем стабильный порядок регистрации как tie-breaker;
- документированные диапазоны/конвенции или именованные точки конвейера, если одного числа недостаточно;
- тесты, проверяющие реальный порядок вызовов и поведение middleware, а не только порядок перечисления объектов.

### Ограничения числового Order

Числовой приоритет прост, но плохо выражает причинные зависимости: авторизация должна идти после аутентификации, а обработчик исключений должен оборачивать middleware, ошибки которого он обязан обрабатывать. Одинаковые числа требуют стабильного tie-breaker, отрицательные и большие значения без соглашений превращаются в скрытую договорённость.

Поэтому начать следует с `Order` и стабильной сортировки только если реальные сценарии показывают, что текущего порядка регистрации недостаточно. Для обязательных зависимостей (например, authentication before authorization) позднее можно добавить явные ограничения порядка/проверки конфликтов. Не следует смешивать порядок регистрации DI-сервисов с порядком middleware: это разные этапы жизненного цикла.

## 6. Диагностические endpoints

Для хоста рекомендуется раздельно настроить liveness и readiness:

- liveness отвечает на вопрос, жив ли процесс, и не должен становиться неуспешным только из-за временной недоступности БД;
- readiness проверяет зависимости, без которых данный хост не способен обслуживать запросы; набор проверок задаёт хост исходя из своих требований;
- подробные диагностические endpoints и UI следует ограничивать по окружению и/или авторизации, не раскрывая строки подключения, исключения и другие секреты;
- Swagger обычно включается по умолчанию только в Development, если хост явно не выбрал другую политику.

Это рекомендации для хоста, а не утверждение, что все проверки должны автоматически включаться платформой.


## Реализовано: порядок middleware и диагностика

- `IPlatformWebFeature` и `IWebModule` предоставляют `Order` со значением по умолчанию `500`.
- `UseModules()` конфигурирует их в общем порядке: `Order` по возрастанию; при равном значении features перед веб-модулями, внутри вида сохраняется порядок регистрации.
- `DefaultExceptionHandler` подключается платформой в начале конвейера и не участвует в сортировке.
- Health checks опубликованы как `/health/live` (без выполнения проверок зависимостей) и `/health/ready` (все проверки, зарегистрированные хостом). Health Checks UI опрашивает readiness.
- Защита диагностических endpoint не встроена; её должен настроить хост/инфраструктура.

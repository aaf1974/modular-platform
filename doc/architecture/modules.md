# Модули: регистрация, зависимости и жизненный цикл

## Контракт модуля

Каждый модуль реализует `Platform.Core.Modules.IModule`:

```csharp
public interface IModule
{
    void RegisterServices(ModuleContext context);
}
```

Регистрация выполняется через `IServiceCollection.AddModule<TModule>(configuration, environmentName)`. Тип `TModule` должен быть классом, реализующим `IModule`, и иметь публичный конструктор без параметров (`new()`).

## Что доступно в `ModuleContext`

Контекст передаётся в `RegisterServices()` и предоставляет коллекцию DI-сервисов, `IConfiguration` и имя окружения. Модуль должен регистрировать зависимости в переданной коллекции, не строя отдельный контейнер.

## Фактический порядок регистрации

1. Проверяются аргументы и отсутствие ранее зарегистрированного типа модуля.
2. Создаётся экземпляр модуля.
3. Если модуль реализует `IModuleDependencies`, считывается и проверяется список зависимостей: он не должен быть `null`, содержать `null`, типы вне `IModule`, повторяющиеся типы или сам модуль.
4. Создаётся `ModuleContext`.
5. Вызывается `RegisterServices(context)`.
6. Если `RegisterServices` выбрасывает исключение, коллекция `IServiceCollection` восстанавливается к состоянию до вызова, после чего исходное исключение пробрасывается дальше.
7. При успешном выполнении экземпляр регистрируется как singleton `IModule`, а сведения о типе и зависимостях сохраняются в `ModuleRegistration`.

Откат касается коллекции DI-дескрипторов. Он не может автоматически отменить внешние побочные эффекты, которые модуль мог выполнить в `RegisterServices()`.

## Обязательные зависимости

Модуль может реализовать `IModuleDependencies` и вернуть типы модулей, которые должны быть зарегистрированы. `ValidateModules()` проверяет, что все указанные типы присутствуют среди зарегистрированных модулей.

- Метод проверяет наличие зависимостей, но не регистрирует их автоматически.
- Проверка выполняется по точным типам модулей.
- Проверка не анализирует зависимости обычных DI-сервисов.
- Текущий код не проверяет циклы между модулями и не сортирует модули топологически.
- В Demo.Api `ValidateModules()` сейчас не вызывается; при добавлении модулей с `IModuleDependencies` приложение должно вызвать его после всех `AddModule` и до `Build()`.

## Порядок

Состав и порядок регистрации задаёт приложение. Веб-интеграция получает зарегистрированные `IModule` в порядке, в котором их вернул контейнер DI; стандартная регистрация singleton-дескрипторов сохраняет порядок регистрации.

Различие системных и бизнес-модулей, а также идея собственного builder API и `BuildPlatform()` описаны как предложения в [документе развития архитектуры](architecture-evolution-proposals.md). Пока это не отдельные runtime-контракты платформы.

## Ограничения и рекомендации

- Регистрируйте каждый тип модуля один раз на контейнер.
- Не вызывайте `BuildServiceProvider()` внутри регистрации модуля.
- Выполняйте регистрацию сервисов до `Build()`.
- Не создавайте второй экземпляр модуля для HTTP-конфигурации: `UseModules()` использует экземпляры `IModule`, зарегистрированные при `AddModule`.
- Не используйте `IModule` как глобальный реестр бизнес-сервисов.
- Модули без веб-функциональности не обязаны ссылаться на `Platform.AspNetCore`.

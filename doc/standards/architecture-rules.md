# Архитектурные правила

Этот документ содержит краткие правила, которые должны сохраняться при развитии платформы. Подробные объяснения находятся в тематических документах.

## Модули

1. Приложение явно регистрирует используемые модули; автоматическое обнаружение модулей не является частью текущего API.
2. Каждый модуль реализует `IModule` и регистрирует сервисы в переданном `ModuleContext`.
3. Повторная регистрация одного типа модуля в одном контейнере запрещена.
4. Обязательные зависимости объявляются через `IModuleDependencies` и проверяются вызовом `ValidateModules()`. Этот вызов должен быть добавлен в composition root, если используются такие зависимости.
5. Модуль не должен строить отдельный DI-контейнер или вызывать `BuildServiceProvider()` для разрешения собственных зависимостей.
6. Внутренняя реализация модуля не должна становиться зависимостью других модулей без явного архитектурного решения; для межмодульного API предпочтительны публичные контракты.

## ASP.NET Core

1. Регистрация сервисов выполняется до `Build()`, настройка HTTP — после `Build()`.
2. Модуль реализует `IWebModule` только при наличии HTTP-функциональности.
3. `UseModules()` вызывается один раз для каждого экземпляра `WebApplication`.
4. WebFeature настраиваются раньше веб-модулей; оба набора обходятся в порядке регистрации.
5. Приложение отвечает за положение `UseModules()` относительно остального middleware.
6. Повторная регистрация одного и того же экземпляра `IPlatformWebFeature` запрещена.

## EF Core

1. Провайдер БД и строку подключения выбирает приложение.
2. Модуль предоставляет EF-конфигурации через `IEfModule.ConfigurationAssemblies`; не следует сканировать произвольные сборки.
3. Набор модулей, влияющих на модель, должен быть определён до первого использования модели и не меняться в рамках одного приложения.
4. Репозитории и CRUD-сервис не фиксируют изменения самостоятельно; единицу сохранения контролирует прикладной сценарий.
5. Аудит и soft delete выполняются `ApplicationDbContext` для сущностей, реализующих соответствующие контракты.
6. Использование `IgnoreQueryFilters()` требует осторожности: оно отключает все глобальные фильтры запроса.

## Тесты и документация

1. Изменения архитектурного контракта сопровождаются тестами и обновлением документации.
2. PostgreSQL-специфичное поведение проверяется на PostgreSQL, в том числе через Testcontainers.
3. Примеры должны соответствовать текущему API. Целевые, ещё не реализованные механизмы должны быть явно помечены.
4. Не считать правило автоматически обеспеченным только потому, что оно записано в документации.

# Правила архитектуры и разработки модулей Platform

## 1. Общие принципы

1. Платформа разрабатывается на .NET 10.
2. Приложение состоит из ядра платформы, интеграционных расширений и подключаемых функциональных модулей.
3. Приложение самостоятельно определяет, какие модули используются.
4. Подключение модулей выполняется явно в `Program.cs`.
5. Модуль может состоять из одной или нескольких сборок.
6. Модуль самостоятельно регистрирует необходимые сервисы, настройки и инфраструктурные компоненты.
7. Внутренняя реализация модуля скрыта от других модулей.
8. Взаимодействие между модулями осуществляется преимущественно через публичные контракты.
9. Ядро платформы содержит общие механизмы и абстракции, но не реализует бизнес-функциональность.
10. Используются стандартные механизмы .NET: Microsoft DI, `IConfiguration`, Options Pattern, ASP.NET Core и EF Core.
11. Автоматическое обнаружение модулей и сканирование сборок не выполняются.
12. Порядок подключения модулей определяется приложением.
13. Публичные API платформы и модулей должны иметь XML-документацию.

## 2. Структура платформы

### 2.1. Platform.Core

Содержит:
- Контракт `IModule`.
- Контекст регистрации `ModuleContext`.
- Механизм регистрации модулей.
- Проверку повторной регистрации.
- Объявление и проверку обязательных зависимостей модулей.

Не содержит:
- Бизнес-логики.
- Зависимостей от ASP.NET Core.
- Зависимостей от EF Core.
- HTTP-маршрутов и middleware.
- Реализации конкретного брокера сообщений.

### 2.2. Platform.AspNetCore

Содержит:
- Контракт `IWebModule`.
- Контекст веб-модуля `WebModuleContext`.
- Интеграцию модулей с `WebApplicationBuilder`.
- Настройку веб-модулей после `Build()`.
- Возможность регистрации endpoints и middleware.

### 2.3. Platform.EntityFrameworkCore

Содержит интеграционные механизмы для EF Core:
- Общие соглашения конфигурации сущностей.
- `ApplicationDbContext` — единый контекст для сущностей всех подключённых модулей.
- Регистрацию общего контекста и вспомогательные средства подключения конфигураций.
- Интеграционные возможности для модулей, использующих EF Core.

Приложение выбирает провайдер базы данных и задаёт строку подключения. Для PostgreSQL приложение подключает провайдер Npgsql и настраивает контекст через `UseNpgsql`; `Platform.EntityFrameworkCore` не должен зависеть от конкретного провайдера.

### 2.4. Platform.Events.Abstractions

Содержит контракты событий и обработчиков, не зависящие от транспорта доставки.

### 2.5. Platform.Events.InProcess

Содержит реализацию доставки событий внутри процесса.

В дальнейшем допускаются адаптеры для внешних брокеров сообщений без изменения публичных бизнес-контрактов модулей.

## 3. Контракт модуля

Каждый подключаемый модуль реализует `IModule`.

```csharp
namespace Platform.Core.Modules;

/// <summary>
/// Определяет контракт функционального модуля платформы.
/// </summary>
public interface IModule
{
    /// <summary>
    /// Регистрирует сервисы и зависимости модуля.
    /// </summary>
    /// <param name="context">Контекст регистрации модуля.</param>
    void RegisterServices(ModuleContext context);
}
```

Правила:

1. Модуль создаётся механизмом регистрации посредством `new TModule()`.
2. Тип модуля должен реализовывать `IModule` и иметь публичный конструктор без параметров.
3. `RegisterServices()` вызывается до `Build()`.
4. Внутри `RegisterServices()` модуль регистрирует необходимые сервисы, настройки и инфраструктурные зависимости.
5. Регистрация сервисов не означает немедленного создания всех зарегистрированных сервисов.
6. Исключения при регистрации должны приводить к понятной ошибке запуска.
7. При ошибке регистрации модуль не считается успешно подключённым.
8. Повторная регистрация одного типа модуля в пределах одного контейнера DI запрещена.
9. Ошибки регистрации не должны маскироваться необоснованной заменой исходного исключения.

## 4. Контекст регистрации

`ModuleContext` предоставляет модулю доступ к:

- `IServiceCollection Services`.
- `IConfiguration Configuration`.
- `string EnvironmentName`.

Контекст предназначен для регистрации зависимостей и чтения конфигурации.

Правила:

1. Модуль самостоятельно регистрирует свои сервисы.
2. Используется стандартный контейнер Microsoft DI.
3. Модуль самостоятельно выбирает время жизни своих сервисов.
4. Модуль не должен самостоятельно строить промежуточный контейнер DI через `BuildServiceProvider()`.
5. Обязательные настройки проверяются при запуске.
6. Для типизированных настроек рекомендуется Options Pattern.
7. Необязательные зависимости не должны ошибочно трактоваться как обязательные.

## 5. Зависимости между модулями

1. Зависимости объявляются явно через публичные контракты модулей.
2. Приложение самостоятельно определяет состав подключаемых модулей.
3. Ядро не строит автоматически граф зависимостей и не разрешает зависимости вместо приложения.
4. Обязательные зависимости должны проверяться до `Build()`.
5. Отсутствие обязательной зависимости должно приводить к понятной ошибке.
6. Проверка зависимостей не должна изменять коллекцию сервисов.
7. Ошибки валидации должны содержать достаточно информации для определения отсутствующего модуля или контракта.
8. Необязательные зависимости допускаются и должны явно отличаться от обязательных.
9. Модуль должен зависеть от публичных контрактов, а не от внутренних реализаций других модулей.
10. Приложение отвечает за подключение необходимых модулей и реализаций контрактов.

## 6. Жизненный цикл модулей

Жизненный цикл состоит из двух основных этапов.

### 6.1. Регистрация сервисов

Выполняется до `builder.Build()`.

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.AddModule<AuthenticationModule>();
builder.AddModule<BusinessModule>();

builder.ValidateModules();

var app = builder.Build();
```

На этом этапе:
- Создаются экземпляры модулей.
- Выполняется `RegisterServices()`.
- Регистрируются сервисы в DI.
- Проверяются обязательные зависимости.

Регистрация сервисов и создание экземпляров сервисов — разные процессы. Большинство сервисов создаётся контейнером при разрешении соответствующих зависимостей.

### 6.2. Настройка веб-приложения
Выполняется после `Build()`.

```csharp
app.UseModules();

app.Run();
```

На этом этапе веб-модули:
- Регистрируют HTTP endpoints.
- Добавляют middleware.
- Настраивают другие компоненты ASP.NET Core.

Модули без HTTP-функциональности не обязаны реализовывать `IWebModule`.

## 7. Правила Platform.AspNetCore

### 7.1. Контракт IWebModule

`IWebModule` — необязательный контракт для модулей, которым требуется настраивать HTTP-конвейер.

```csharp
namespace Platform.AspNetCore.Modules;

/// <summary>
/// Определяет контракт модуля, настраивающего HTTP-конвейер приложения.
/// </summary>
public interface IWebModule
{
    /// <summary>
    /// Настраивает HTTP-конвейер и endpoints приложения.
    /// </summary>
    /// <param name="context">
    /// Контекст, предоставляющий доступ к построенному веб-приложению.
    /// </param>
    void ConfigureApplication(WebModuleContext context);
}
```

Правила:

1. Веб-модуль может регистрировать endpoints.
2. Веб-модуль может добавлять middleware.
3. Веб-модуль может использовать стандартные механизмы ASP.NET Core.
4. Модуль не должен предполагать, что его middleware будет подключён в произвольном порядке.
5. Модуль должен учитывать требования к положению своего middleware в HTTP-конвейере.
6. Порядок вызова `ConfigureApplication()` соответствует порядку регистрации модулей.
7. Приложение отвечает за положение `UseModules()` относительно middleware, добавляемого самостоятельно.
8. `Platform.Core` не должен зависеть от `IWebModule` или других HTTP-абстракций.

### 7.2. Контекст веб-модуля

`WebModuleContext` предоставляет доступ к:

- `WebApplication Application`.
- `IServiceProvider Services`.
- `IConfiguration Configuration`.
- `IHostEnvironment Environment`.

Контекст предназначен для настройки уже построенного веб-приложения.

Регистрация новых сервисов через `IServiceCollection` на этом этапе не предусматривается.

### 7.3. Порядок middleware

1. Порядок вызова `ConfigureApplication()` определяется порядком подключения модулей.
2. Порядок middleware внутри HTTP-конвейера определяется последовательностью вызовов методов ASP.NET Core.
3. `UseModules()` не гарантирует автоматически правильный порядок относительно middleware, зарегистрированного приложением.
4. Аутентификация должна быть настроена до авторизации, если этого требует используемая конфигурация ASP.NET Core.
5. Модули не должны самостоятельно переставлять уже зарегистрированные компоненты конвейера.
6. Требования к взаимному порядку middleware должны быть определены до реализации сложных модулей авторизации, аудита и обработки запросов.

### 7.4. Повторные вызовы

1. Повторный `AddModule<TModule>()` для уже зарегистрированного типа модуля запрещён.
2. Повторный `UseModules()` для одного экземпляра `WebApplication` запрещён.
3. Повторный вызов `UseModules()` должен завершаться понятным `InvalidOperationException`.
4. Запрет повторного вызова действует и в случае, если предыдущая настройка завершилась исключением: часть конфигурации могла уже примениться.
5. Разные экземпляры `WebApplication` должны иметь независимое состояние настройки модулей.
   Важно: ValidateModules() в примере предполагает наличие соответствующего метода в реализации. Если он ещё не реализован в текущей версии платформы, этот вызов пока является целевым API, а не готовой возможностью.

## 8. Dependency Injection

1. Используется стандартный контейнер `Microsoft.Extensions.DependencyInjection`.
2. Каждый модуль самостоятельно регистрирует свои сервисы.
3. Время жизни сервисов определяется назначением конкретного сервиса.
4. Регистрация модулей и создание экземпляров сервисов — разные этапы.
5. Один экземпляр модуля используется и для регистрации сервисов, и для настройки HTTP.
6. Механизм веб-интеграции не должен создавать дополнительные экземпляры уже зарегистрированных модулей.
7. Ядро не вводит собственный контейнер DI, глобальный реестр бизнес-сервисов или обязательные соглашения об именовании.
8. Модуль не должен самостоятельно строить промежуточный контейнер DI через `BuildServiceProvider()`.
9. Регистрация сервисов должна выполняться до `Build()`.
10. Настройка HTTP выполняется после `Build()`.

## Аудит сущностей и мягкое удаление

1. `Platform.EntityFrameworkCore` предоставляет контракт `ICurrentUser`. Его свойство `UserId` имеет тип `string?`: `null` означает, что текущий пользователь не определён; фиктивные значения вроде `Guid.Empty` не используются.
2. Платформа регистрирует `StubCurrentUser` по умолчанию. Модуль аутентификации может зарегистрировать собственную реализацию `ICurrentUser`; при регистрации нескольких реализаций приложение должно контролировать порядок регистрации и разрешаемую реализацию.
3. Контракт текущего пользователя не зависит от модели пользователя модуля Authentication и не создаёт внешних ключей к его таблицам.
4. Сущности подключают аудит выборочно через `ICreatedAt`, `IModifiedAt`, `ICreatedBy` и `IModifiedBy`. Платформа заполняет соответствующие поля при `SaveChanges` и `SaveChangesAsync`.
5. Временные метки аудита задаются в UTC. Для PostgreSQL следует использовать совместимое отображение UTC-значений, в частности `timestamp with time zone` (`timestamptz`) для `DateTime` со значением `DateTimeKind.Utc`.
6. `ISoftDeletable` добавляет `IsDeleted`, `DeletedAtUtc` и `DeletedByUserId`. Вызов `Remove` для такой сущности превращается в мягкое удаление.
7. Для `ISoftDeletable` платформа применяет глобальный фильтр, исключающий удалённые записи. Явный запрос с `IgnoreQueryFilters()` может отключить все глобальные фильтры сущности, включая фильтры, добавленные модулем; использовать его следует осознанно.
8. Репозитории и сервисы не вызывают `SaveChanges` самостоятельно. Единицей фиксации остаётся прикладной сценарий, который может объединять несколько изменений.
9. Аудит и мягкое удаление должны проверяться интеграционными тестами на PostgreSQL через Testcontainers; InMemory-тесты не заменяют проверку поведения целевой СУБД.

## 9. Работа с EF Core

### 9.1. Общие правила

1. `Platform.EntityFrameworkCore` предоставляет конкретный `ApplicationDbContext`, общий для сущностей всех подключённых модулей.
2. Регистрация платформенной EF Core-инфраструктуры предоставляет и scoped-разрешение `ApplicationDbContext`, и `IDbContextFactory<ApplicationDbContext>` для создания контекста по требованию.
3. Модули владеют своими сущностями и предоставляют конфигурации через `IEntityTypeConfiguration<TEntity>` и `IEfModule`.
4. Модуль не обязан использовать EF Core.
5. Модули не должны самостоятельно изменять уже построенную EF-модель.
6. Модель объединяет конфигурации только явно зарегистрированных модулей; автоматическое сканирование модулей запрещено. Сканирование сборок EF-конфигураций разрешено только для сборок, явно предоставленных модулем.
7. Приложение выбирает EF Core-провайдер и задаёт строку подключения. Для PostgreSQL используется Npgsql/`UseNpgsql` на уровне приложения.
8. Набор модулей, формирующих модель `ApplicationDbContext`, должен быть определён при запуске приложения и оставаться неизменным в течение жизни этого приложения.
9. Модуль не должен самостоятельно управлять общей моделью приложения за пределами предоставленных ему механизмов конфигурации.
10. Платформа предоставляет общий `IEntityId<TId>` без фиксации единого типа ключа для всех сущностей.
11. По умолчанию DI регистрирует `IRepository<TEntity, TId>`, `IEfRepository<TEntity, TId>` и `ICrudService<TEntity, TId>` как scoped открытые generic-сервисы через `TryAddScoped`.
12. Для замены стандартной реализации конкретной сущности модуль регистрирует закрытый generic-сервис, например `IRepository<Order, int>`. В стандартном Microsoft DI закрытая регистрация имеет приоритет над регистрацией открытого generic-типа независимо от того, добавлена она до или после `AddPlatformEntityFrameworkCore`.
13. Если заменяется сама открытая generic-реализация (например, `IRepository<,>` для всех сущностей), пользовательскую регистрацию можно добавить до или после `AddPlatformEntityFrameworkCore`: до — `TryAddScoped` не добавит платформенный default; после — последняя подходящая открытая регистрация будет выбрана Microsoft DI. Если замена нужна только отдельному модулю, предпочтительнее закрытая регистрация конкретного типа сущности.
14. `IRepository<TEntity, TId>` и `IEfRepository<TEntity, TId>` — независимые DI-контракты. Замена одного не заменяет другой автоматически. `CrudService<TEntity, TId>` зависит от `IRepository<TEntity, TId>` и использует выбранную DI реализацию этого контракта.
15. Репозиторий предоставляет типовые операции получения по ID, постраничного списка и изменения состояния сущности. Размер страницы ограничен диапазоном 1–500 записей.
16. `IRepository<TEntity, TId>` не раскрывает `IQueryable`. EF-специфичные запросы доступны через `IEfRepository<TEntity, TId>`; для сложных сценариев предпочтительны специализированные репозитории/запросы модуля. Стандартный список сортируется по ID перед пагинацией.
17. `IEfRepository.QueryIncludingDeleted()` отключает все глобальные фильтры EF Core для соответствующего запроса, а не только фильтр soft delete. Использовать его следует осознанно.
18. CRUD-сервис делегирует стандартные операции репозиторию и не вызывает `SaveChanges` самостоятельно. Бизнес-валидация и специализированные операции остаются ответственностью сервисов конкретных модулей.

### 9.2. Тестирование EF Core

1. Модульные тесты проверяют логику без запуска СУБД.
2. Интеграционные тесты, зависящие от поведения PostgreSQL, используют PostgreSQL через Testcontainers.
3. Тестовые EF-конфигурации для проверки сканирования сборок должны находиться в изолированных fixture-сборках, чтобы случайные конфигурации из тестовой сборки не попадали в модель.
4. Контейнер следует переиспользовать в пределах набора интеграционных тестов; данные между тестами должны изолироваться явно.

### 9.3. Миграции

1. Владение миграциями определяется приложением либо специально выделенным проектом миграций.
2. Миграции должны соответствовать итоговой модели конкретного приложения.
3. Подключение нового модуля может потребовать создания новых миграций.
4. Модули не должны самостоятельно применять миграции общей базы данных при обычной регистрации сервисов.

### 9.4. Межмодульные связи

1. Прямые связи между сущностями разных модулей допускаются только как осознанное архитектурное решение.
2. По умолчанию межмодульное взаимодействие выполняется через публичные контракты и сервисы.
3. Модуль не должен зависеть от внутренних типов сущностей другого модуля без явного архитектурного обоснования.
4. Общая модель базы данных не отменяет логическую изоляцию модулей.

## 10. Взаимодействие между модулями

Предусматриваются три возможных механизма:

1. **Синхронное взаимодействие** через интерфейсы и сервисы.
2. **События** для уведомления о произошедших фактах.
3. **Команды и запросы** для выполнения операций и получения данных, если возникнет необходимость в отдельной модели.

### 10.1. Публичные контракты

1. Контракты отделены от внутренних реализаций.
2. Потребители зависят от интерфейсов и DTO, а не от конкретных классов реализации.
3. Контракт должен содержать только те сведения, которые необходимы потребителям.
4. Изменение внутренней реализации модуля не должно требовать изменений потребителей, если публичный контракт остаётся прежним.

### 10.2. События

1. Абстракции событий не зависят от транспорта доставки.
2. Первая реализация доставки может работать внутри процесса.
3. События описывают произошедшие факты, например `UserRegistered`.
4. Реализация доставки и обработчики событий должны быть отделены от бизнес-контрактов.
5. Подключение внешнего брокера не должно требовать изменения бизнес-смысла существующих событий.

При переходе к внешней доставке необходимо отдельно определить:
- Формат и версионирование сообщений.
- Правила повторной доставки.
- Идемпотентность обработчиков.
- Обработку дубликатов.
- Гарантии доставки.
- Обработку ошибок и недоступности потребителей.

Отдельная инфраструктура команд и запросов не вводится до появления обоснованной потребности.

## 11. Конфигурация

1. Каждый модуль самостоятельно получает настройки через `IConfiguration`.
2. Для типизированных настроек рекомендуется Options Pattern.
3. Допускается использование `IOptions<T>`, `IOptionsSnapshot<T>` и `IOptionsMonitor<T>` в соответствии с назначением сервиса.
4. Обязательные настройки должны проверяться при запуске.
5. Отсутствие обязательной настройки должно приводить к понятной ошибке.
6. Ошибки конфигурации должны содержать сведения, позволяющие определить модуль и проблемную настройку.
7. Модуль не должен незаметно подменять отсутствующие обязательные настройки произвольными значениями.
8. Настройки одного модуля не должны бесконтрольно изменять конфигурацию других модулей.

## 12. Диагностика и проверки состояния

1. Для ASP.NET Core используется стандартная инфраструктура Health Checks.
2. Модули могут регистрировать собственные проверки готовности и состояния зависимостей.
3. Приложение определяет набор проверок, влияющих на состояние приложения.
4. Приложение определяет, какие endpoints публикуют результаты проверок.
5. Liveness и readiness имеют разные назначения:
    - Liveness показывает, функционирует ли процесс приложения.
    - Readiness показывает, готово ли приложение принимать запросы с учётом необходимых зависимостей.
6. Модуль не должен самостоятельно публиковать диагностические endpoints без согласования с правилами приложения.
7. Проверки состояния не должны без необходимости выполнять дорогостоящие операции или изменять данные.


## 13. Правила разработки и тестирования

### 13.1. Документация

1. Публичные API платформы и модулей документируются через XML-комментарии.
2. XML-документация должна описывать назначение типов, интерфейсов, методов, параметров и возвращаемых значений.
3. Для публичных API необходимо указывать исключения, если они являются частью ожидаемого поведения.
4. При изменении публичного API соответствующая документация обновляется.
5. Примеры кода в документации должны соответствовать текущей реализации платформы.

### 13.2. Модульные тесты

1. Каждый существенный архитектурный контракт должен проверяться тестами.
2. Проверяются успешная регистрация модулей и обработка ошибок.
3. Проверяется поведение при повторной регистрации одного типа модуля.
4. Проверяется поведение при исключении из `RegisterServices()`.
5. Проверяется корректность проверки обязательных зависимостей.
6. Проверяется сохранение порядка регистрации модулей.
7. Проверяется, что один экземпляр модуля используется на протяжении предусмотренного жизненного цикла.
8. Тесты не должны зависеть от общего изменяемого статического состояния без необходимости.

### 13.3. Тестирование веб-интеграции

1. Проверяется настройка веб-модулей после `Build()`.
2. Проверяется регистрация endpoints веб-модулем.
3. Проверяется фактическое выполнение middleware при обработке HTTP-запроса.
4. Проверяется порядок настройки веб-модулей.
5. Проверяется повторный вызов `UseModules()`.
6. Проверяется обработка исключений при настройке веб-приложения.
7. Для тестирования HTTP-интеграции предпочтительно использовать тестовый сервер ASP.NET Core.

### 13.4. Требования к тестам

1. Названия тестов должны отражать проверяемое поведение.
2. Атрибуты `Fact` должны содержать понятное описание сценария на русском языке через `DisplayName`.
3. Тесты должны проверять наблюдаемое поведение, а не только внутреннее устройство реализации.
4. После каждого этапа разработки выполняются сборка и тестирование solution.
5. Изменения архитектурных правил сопровождаются обновлением тестов.

Пример:

```csharp
[Fact(DisplayName = "Повторная регистрация одного модуля должна приводить к понятной ошибке")]
public void AddModule_WhenModuleAlreadyRegistered_ThrowsInvalidOperationException()
{
    // Arrange, Act, Assert.
}
```

## 14. Основной сценарий подключения модулей

Предполагаемый сценарий подключения модулей в ASP.NET Core-приложении:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.AddModule<AuthenticationModule>();
builder.AddModule<AuthorizationModule>();
builder.AddModule<BusinessModule>();

// Проверка обязательных зависимостей модулей.
// Метод является частью целевого API, если он ещё не реализован.
builder.ValidateModules();

var app = builder.Build();

// Настройка endpoints и middleware зарегистрированных веб-модулей.
app.UseModules();

app.Run();
```

Правила:

1. Приложение явно определяет состав используемых модулей.
2. Регистрация сервисов выполняется до `Build()`.
3. Обязательные зависимости должны проверяться до построения приложения.
4. Настройка HTTP выполняется после `Build()`.
5. Веб-модули настраиваются в порядке регистрации.
6. Приложение отвечает за положение `UseModules()` относительно других компонентов HTTP-конвейера.
7. Приложение может использовать бизнес-модули без подключения `Platform.AspNetCore`, если этим модулям не требуется HTTP-функциональность.

## 15. Пример структуры сложного модуля

Сложный модуль может состоять из нескольких сборок:

```text
Authentication/
├── Authentication.Contracts/
├── Authentication.Application/
├── Authentication.Infrastructure/
└── Authentication.AspNetCore/
```

Назначение сборок:

- `Authentication.Contracts` — публичные интерфейсы и DTO.
- `Authentication.Application` — сценарии использования и бизнес-логика.
- `Authentication.Infrastructure` — EF Core, хранилища и внешние интеграции.
- `Authentication.AspNetCore` — endpoints, middleware и HTTP-интеграция.

Правила:

1. Модуль не обязан состоять из фиксированного количества сборок.
2. Для небольшого модуля допускается объединение нескольких уровней в одну или две сборки.
3. Контракты не должны зависеть от инфраструктурных реализаций.
4. Инфраструктурная реализация зависит от необходимых контрактов и инфраструктурных библиотек.
5. Приложение выступает точкой композиции модулей и их реализаций.

## 16. Принципы дальнейшего развития платформы

1. Новые абстракции добавляются при наличии конкретной потребности.
2. Базовое ядро остаётся минимальным.
3. HTTP, EF Core и доставка событий остаются отдельными интеграционными слоями.
4. Внутренние реализации модулей не становятся публичными контрактами без необходимости.
5. Порядок регистрации модулей остаётся явным и контролируемым приложением.
6. Сложные механизмы управления зависимостями и порядком middleware не вводятся до появления подтверждённых сценариев.
7. Новые интеграционные возможности не должны создавать обязательные зависимости для модулей, которым они не нужны.
8. Архитектурные изменения сопровождаются обновлением документации и тестов.
9. Реализованные возможности необходимо отличать от запланированных.
10. Примеры кода должны соответствовать фактически доступным API либо явно помечаться как целевые.

### 16.1. Приоритет реализации

Рекомендуемый порядок развития платформы:

1. `Platform.Core` — контракты, регистрация модулей, проверка повторной регистрации и зависимостей.
2. `Platform.Core.Tests` — проверка основных архитектурных правил.
3. `Platform.AspNetCore` — веб-контракт, настройка HTTP и middleware.
4. Демонстрационное приложение — подключение нескольких модулей.
5. `Platform.EntityFrameworkCore` — объединение конфигураций сущностей.
6. `Platform.Events.Abstractions` — контракты событий.
7. `Platform.Events.InProcess` — внутрипроцессная доставка событий.
8. Health Checks и интеграционные тесты.
9. Проверка повторного использования бизнес-модулей в фоновой службе.

## 17. Примечания о текущем состоянии реализации

Документация содержит как реализованные правила, так и архитектурные требования на будущее.

Перед использованием конкретной возможности необходимо убедиться, что соответствующий API реализован и покрыт тестами.

- `ValidateModules()` и механизм проверки обязательных зависимостей.
- Защита от повторного вызова `UseModules()`.
- Сохранение одного экземпляра модуля на протяжении жизненного цикла.
- Декларативное описание требований к порядку middleware.
